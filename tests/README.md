# Testing

Given the multi-language nature of this package, we are dealing with one test suite for each
language. These are discussed individually below.

## Rust

Unittests of Rust crates are included directly in the source code. They can get executed using
`cargo test` for which a simple `make` target is provided in this repo, to ensure that the dynamic
library dependencies get linked correctly:
```bash
make testrust
```

This will run the tests included in the `core` crate which contains all native Rust logic of this
package.
Refer to [this readme](`crates/README.md`) for an explanation of the different crates.

> **Note:** `make testrust` builds the `core` crate with its `cext` feature (linking `qiskit-sys`),
> so — just like the C API — it reads `QISKIT_LIB` and `QISKIT_INCLUDE`, which must resolve to a
> Qiskit **C** library. See the [C installation instructions](../docs/install-c.rst) for how these
> are defaulted and when to set them explicitly. (The Python test target does *not* use them, because
> `pyext` links Qiskit through `qiskit-pyo3-ffi` instead.)

If at some point we start writing integration tests for the Rust API, these should be implemented in
`crates/core/tests` to ensure that `cargo test` will find them.
See also [here](https://doc.rust-lang.org/rust-by-example/testing/integration_testing.html).

## Python

Unittest for the Python API are placed in `tests/python`. Additionally, we should strive for good
examples in the API documentation which is written in the docstrings of the `pyext` crate. These
should be formatted as [doctests](https://docs.python.org/3/library/doctest.html).

All of these tests are detected and run by `pytest` for which another simple `make` target exists:
```bash
make testpython
```

Note, that this target requires compilation of the `pyext` crate which not only ensures that the
compiled Rust code is up-to-date but also re-generates the Python stub files via the
[`pyo3-stub-gen` crate](https://crates.io/crates/pyo3-stub-gen). These Python type information files
contain the API documentation and therefore must be updated for the doctests to be up-to-date.

### Type stubs (`.pyi`)

The package ships as [PEP 561](https://peps.python.org/pep-0561/) typed (note the `py.typed` marker
and the `Typing :: Typed` classifier). Typing is provided in two ways, and it is worth understanding
which is which:

- The **pure-Python** modules under `python/qiskit_fermions/` are typed *inline* — the annotations
  live in the `.py` sources. Do **not** write or generate `.pyi` files for them (e.g. with
  `stubgen`); that would duplicate the annotations and drift.
- The **compiled `pyext` extension** cannot carry inline annotations, so its types live in `.pyi`
  stubs generated by `pyo3-stub-gen` (`make pystubs` / `make pystubs-dev`).

Three things about those generated stubs are easy to get wrong, so they are worth spelling out:

1. **They are rooted at `qiskit_fermions._lib`, not the public paths.** The extension module is
   `#[pymodule] _lib`, so every `#[gen_stub_*(module = "...")]` in `crates/pyext/src` uses the
   *physical* runtime path (`qiskit_fermions._lib....`), and `stub_info()` in
   `crates/pyext/src/lib.rs` is rooted there too. The stubs therefore land under
   `python/qiskit_fermions/_lib/**`, which has no hand-written `__init__.py`. This is deliberate: if
   the stubs were emitted at the public paths (`qiskit_fermions.operators`, …), the generated
   `__init__.pyi` would sit next to — and *shadow* — the hand-written `__init__.py`, hiding every
   re-exported symbol from type checkers. The public API is typed by the hand-written `__init__.py`
   re-exports, which import from `_lib` and are read by type checkers directly. (See
   [`jij-inc/pyo3-stub-gen#416`](https://github.com/Jij-Inc/pyo3-stub-gen/pull/416) and
   [`#417`](https://github.com/Jij-Inc/pyo3-stub-gen/issues/417) for the upstream rationale.)
   Note also that `#[pyclass(module = "...")]` keeps the *public* path (so runtime `__module__`,
   `repr`, and error messages stay user-facing) while a separate `#[gen_stub(module = "...")]` gives
   the stub its physical `_lib` path.

2. **They are committed, and never hand-edited.** The `_lib/**/*.pyi` files are checked into git so
   they ship in the wheel (via the `_lib/**/*.pyi` entry in `[tool.setuptools.package-data]`)
   without requiring a Rust toolchain at build time. They are *generated output*: edit the Rust
   docstrings / signatures in `crates/pyext/src` and re-run `make pystubs`, never edit a `.pyi` by
   hand. The `.gitattributes` entry marks them `linguist-generated` as a reminder.

3. **`make lint` fails if they are stale.** The `pystubs-check` target regenerates the stubs and
   runs `git diff --exit-code` over them, so any drift (a forgotten `make pystubs`, or a manual
   edit) turns the lint job red. `make pystubs` always wipes the tree first (via `pystubs-clean`) so
   that stubs for renamed or removed modules cannot linger.

## C

Tests for the C API are placed in `tests/c` and they get executed via `ctest` which in turn is built
with `cmake` (see also [here](https://cmake.org/cmake/help/book/mastering-cmake/chapter/Testing%20With%20CMake%20and%20CTest.html)).
Again, there is a simple `make` target for this:
```bash
make testc
```

This in turn requires compilation of the `cext` crate which also ensures that the C header file gets
updated via [`cbindgen`](https://github.com/mozilla/cbindgen).

> **Note:** like `make testrust`, this links `qiskit-sys` against the Qiskit **C** library, so it
> reads `QISKIT_LIB` and `QISKIT_INCLUDE` (see the
> [C installation instructions](../docs/install-c.rst)).
