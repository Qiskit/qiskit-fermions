# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`qiskit-fermions` extends Qiskit with tools for fermionic systems. Following Qiskit's design philosophy: the **core is written in Rust**, with **first-party bindings for both Python and C**, and APIs designed to feel like Qiskit's.

Scope: operator data structures, a framework + library for operator conversion (mappers), and a framework + library for quantum-circuit synthesis.

## Repository layout note

This checkout is a **bare repo + worktrees** setup. The project source lives in the `main/` worktree (and other named worktrees like `apply-unitary/`, `term-ordering/`), *not* in the top-level directory which only holds `.bare/` and the worktree dirs. Run commands and edit files inside a worktree (e.g. `main/`).

## Three-layer crate architecture

The Rust workspace (`crates/`) has three primary crates whose **module structure all mirrors the public Python API** for easy navigation:

- **`core`** — all native logic (operators, mappers, linalg, random). **Must NOT depend on `pyo3`.** This keeps the Rust core cleanly separable from Python so the C API can be Python-independent. Its FFI backend is feature-gated: the `cext` feature pulls in `qiskit-sys`, the `pyext` feature pulls in `qiskit-pyo3-ffi`, and both dependencies are otherwise optional (default = neither).
- **`pyext`** — the public **Python** API built on `core` via `pyo3`. Exposes a `#[pymodule] _lib` whose nested modules are registered into `sys.modules` at import time by `python/qiskit_fermions/__init__.py`. Depends on `core` with its `pyext` feature and links Qiskit through `qiskit-pyo3-ffi` (no locally compiled Qiskit binary required — this is what unlocks Windows support).
- **`cext`** — the public **C** API built on `core`. The C header is generated by `cbindgen` during the build. Depends on `core` with its `cext` feature and links Qiskit's compiled core through `qiskit-sys`.

Two vendored support crates:
- **`qiskit-sys`** — temporarily vendored from `qiskit-rs`; raw bindgen FFI into Qiskit's compiled acceleration library (used by the `cext` backend). Carries no Cargo features of its own anymore.
- **`qiskit-pyo3-ffi`** — Qiskit's PyO3 FFI crate, vendored until published (used by the `pyext` backend). Excluded from lint/typos checks; don't hand-edit.

> The `cext` and `pyext` features of `qiskit-fermions-core` select **mutually exclusive FFI backends** (`qiskit-sys` versus `qiskit-pyo3-ffi`) and must never be unified into one build — enabling both trips a `compile_error!` in `crates/core/src/lib.rs`. This is also why `make lint` clippy-checks each backend as a separate compilation unit rather than running `cargo clippy --all-targets` over the whole workspace.

### Adding a feature (the intended pattern)

1. Implement + test in the Rust `core` crate (minimal internal docs; Rust API is not public).
2. Expose via `pyext` with tests in `tests/python/` and full API docs (docstrings live in the `pyext` Rust source).
3. Expose via `cext` with tests in `tests/c/` and API docs.

This full triple is not always worthwhile — decide case-by-case. Features may also be implemented in the Python API directly first and refactored down to `core` later.

## Build & test

**Always use the Makefile targets, not raw `cargo`** — the Makefile exports `QISKIT_LIB` and `QISKIT_INCLUDE` that the FFI crates need to link. Qiskit must be installed in the same environment.

> **`QISKIT_LIB`/`QISKIT_INCLUDE`.** These point at the Qiskit **C** library, and which builds read them follows directly from the FFI backend (see the crate architecture above):
> - **Python builds (`pyext`)** — `make pyext`, `make pyext-dev`, `make pystubs`, `make testpython`, … — link Qiskit through `qiskit-pyo3-ffi` and **do not read** these vars at all.
> - **C API and Rust-core builds (`cext`)** — `make cext`, `make testc`, **`make testrust`** (`cargo test -p qiskit-fermions-core --no-default-features --features cext`), and also `make lint`/`make docs` (which build the `cext` backend transitively) — link `qiskit-sys` against the Qiskit **C** library and read these vars. The Makefile defaults them via `?=` to the installed `qiskit` package's C artifacts (`qiskit.capi.get_lib()`/`get_include()`), which works when that package ships a usable C library. When it does not — or you want to build/test against a separately compiled Qiskit C API — **override them**, e.g. `QISKIT_LIB=$(find "$(pwd)"/build/qiskit/dist/c/lib/libqiskit.*) QISKIT_INCLUDE="$(pwd)"/build/qiskit/dist/c/include`. See `docs/install-c.rst` for building the Qiskit C API.

| Task | Command |
|------|---------|
| Build Python extension (release) | `make pyext` |
| Build Python extension (dev) | `make pyext-dev` |
| Regenerate `.pyi` stubs | `make pystubs` / `make pystubs-dev` |
| Build C lib + header | `make cext` (needs `QISKIT_LIB`/`QISKIT_INCLUDE` set) |
| Run Rust tests | `make testrust` (core crate, `cext` backend; needs `QISKIT_LIB`/`QISKIT_INCLUDE` set) |
| Run Python tests | `make testpython` |
| Run optional-dependency Python tests | `make testoptional` (needs the optional deps installed — `pip install -e ".[all]"`) |
| Run C tests | `make testc` (needs `QISKIT_LIB`/`QISKIT_INCLUDE` set) |
| Run guide doctests | `make doctest` (only the `docs/guides/` `.rst` files) |
| Lint (rust + python + clang) | `make lint` |
| Auto-fix formatting | `make style` |
| Build docs | `make docs` (Python + C via Doxygen/breathe/Sphinx) |
| Bump version | `make version-bump VERSION=0.2.0.dev0` |

**Running a single Python test:**
```bash
python -m pytest -s -p no:doctest tests/python/operators/test_fermion_operator.py::TestName::test_method
```
(`-p no:doctest` is used because doctests are collected separately via Sybil — see below.)

Editable install for iterating on Python: `SETUPTOOLS_RUST_CARGO_PROFILE=release pip install -e .`

### Important build coupling

`make testpython` recompiles `pyext` and **regenerates the `.pyi` stub files**. The stubs carry the API docstrings *and doctests*, so they must be regenerated for the doctests to reflect current source — and `make testpython` is what actually *runs* those doctests (the docstring/`.pyi` doctests under `python/qiskit_fermions/`, collected via Sybil during a normal `pytest` run). `make testc` likewise recompiles `cext` and regenerates the C header via `cbindgen`.

## Docs & docstrings — where they live

- **Python API docs** are pulled from `python/qiskit_fermions/` source and, for `pyext`-implemented components, from **docstrings written in the `pyext` Rust source** and surfaced through the `.pyi` stubs. Layout config is in `docs/pydoc/`. Docstring convention: **Google** (`ruff` pydocstyle).
- **C API docs**: docstrings written in the `cext` Rust source (mix of Doxygen + Sphinx directives), extracted via Doxygen from the generated header, integrated with breathe. Layout in `docs/cdoc/`.
- **Doctests** are collected by **Sybil** (`python/conftest.py`, `docs/conftest.py`) from `*.py`/`*.pyi`, with `ELLIPSIS | NORMALIZE_WHITESPACE | NUMBER` flags. They run in two places: the docstring and `.pyi`-stub doctests under `python/qiskit_fermions/` run as part of `make testpython` (a normal `pytest` run), while `make doctest` runs *only* the guide doctests in `docs/guides/*.rst` (via `pytest docs/`).

## Testing structure

- **Rust unit tests** live inline in the crate source; run via `make testrust` (only exercises `core`).
- **Python tests** in `tests/python/` (mirrors the API tree: `operators/`, `mappers/`, `circuit/`, `transpiler/`, `linalg/`).
- **C tests** in `tests/c/`, built with CMake and run via `ctest`.
- Tests marked `skipif` (optional deps like `pyomo`/`highspy`) run via `make testoptional`. These deps must actually be installed for the tests to run rather than skip — install the extras, e.g. `pip install -e ".[all]"` (`[all]` pulls in `[optimization]`, i.e. `pyomo`); the extras are declared under `[project.optional-dependencies]` in `pyproject.toml`.

## Transpiler / synthesis plugins

Circuit synthesis is exposed as **stevedore entry points** under `qiskit_fermions.transpiler.synthesis` (see `pyproject.toml` `[project.entry-points]`), e.g. `Evolution.MapperFn`, `OrbitalRotation.GivensDecomposition`. Corresponding pass implementations are in `python/qiskit_fermions/transpiler/passes/synthesis/`.

## Versioning

`VERSION.txt` (committed) is the source of truth for Python; `make version-bump VERSION=...` syncs it with the Rust `Cargo.toml` workspace version and refreshes `Cargo.lock` via `tools/set_version.py`. `version.py` appends a git sha for dev builds and is excluded from coverage. Use PEP 440 forms (`0.2.0.dev0`, `1.0.0rc1`, `1.0.0`).

**Pre-release status:** there is no tagged release yet, so `main` is an **unstable development branch** (see the "under active development" warning at the top of `README.md`). Until the first tagged release lands, we don't track release notes — breaking changes can be made freely and don't need `reno` entries (see the note under Conventions).

## Conventions

- **Every source file requires a copyright header** — `tools/verify_headers.py` enforces this in `make lint` (run over `crates docs python tests tools`, ignoring vendored `crates/qiskit-pyo3-ffi`).
- Python: `ruff` (line-length 100, target py310, Google docstrings), `mypy` (py310).
- Rust: `cargo fmt`, edition 2024, MSRV 1.95.
- C: `clang-format` with `.clang-format`.
- Release notes: managed via `reno` (`releasenotes/`), but **not tracked yet** — no release notes are being written until the first tagged release lands. Until then `main` is an unstable development branch (see Versioning), so new changes don't need a `reno` entry.
